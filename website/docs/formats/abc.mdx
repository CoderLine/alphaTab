## Introduction

> abc notation is a shorthand form of musical notation for computers. In basic form it uses the letters A through G, letter accidentals, and numbers to represent notes, and other elements are used to place composition-wide elements — meter, tempo, key, and so on — and note-specific elements such as ornaments and note lengths.
>
> abc notation was originally intended as a compact ASCII format usable in email, but has grown into a fully-fledged music description language.
>
> [ABC notation standard v2.1](https://abcnotation.com/wiki/abc:standard:v2.1)

**Compatibility Level:** Basic support.

alphaTab reads ABC as piano-style notation. It parses letter+octave pitches, durations against the tune's unit note length, chords, tuplets, grace notes, ties, slurs, bars and repeats, voltas, multi-voice bodies, `%%score` staff grouping, and the common set of decorations and dynamics. ABC's tablature dialects (fret/string notation, custom tab clefs) are outside the v1 scope.

ABC areas that do not have a matching alphaTab model surface are dropped with a diagnostic (via `Logger.warning`) rather than being silently corrupted. This affects, among other things, non-default accidental propagation modes, macro expansion (`m:`), symbol lines (`s:`), part play-order (`P:ABABC`), stylesheet directives beyond `%%score`, and `I:abc-include`. Where an ABC feature can only be approximated (modal keys collapsed to the nearest major/minor, additive meters summed to a single numerator, exotic clefs rounded to the nearest supported clef), the approximation is applied and a warning is emitted so that the loss is visible to callers.

Multi-tune files are supported at detection time but only the first tune is imported; the reference numbers and titles of the remaining tunes are listed in an informational warning. This is a deliberate choice: alphaTab's `Score` carries a single MasterBar timeline, so packing multiple independent tunes into one `Score` would either interleave their bars or leak metadata (title, tempo, key) between tunes.

Fragment input (a music body with no `X:` header) is accepted. A minimal header (`X:1`, `L:1/8`, `K:C`, empty `T:`) is synthesized and a warning identifies the fragment mode. This keeps embedded tutorial snippets and single-line examples usable without requiring callers to wrap them in boilerplate.

The feature table below follows the same conventions as the other format-support docs in this section: the **Data Model** column reflects whether alphaTab's model can represent the concept at all, **Reading** whether the ABC importer parses it, **Rendering** whether alphaTab draws it today, and **Audio** whether it affects playback.

## Feature Table

**How to read the table:**

* Rows are grouped by ABC concept area, roughly mirroring the sections of the [ABC v2.1 spec](https://abcnotation.com/wiki/abc:standard:v2.1).
* Information-field rows use the ABC field letter (e.g. `T:` title, `K:` key).
* Where a row is marked as `Partial`, hover the cell for a short note describing what was dropped or approximated. In all such cases a runtime warning is also emitted by the importer.
* Rows marked as `Ignored` are parsed but produce no runtime effect — this is intentional and covers bibliographic fields, rendering hints alphaTab does not use, and remarks.
* In case of doubt, consult the [ABC v2.1 spec](https://abcnotation.com/wiki/abc:standard:v2.1) and the [alphaTab source](https://github.com/CoderLine/alphaTab/blob/develop/packages/alphatab/src/importer/AbcParser.ts) to see how a specific construct is handled.
